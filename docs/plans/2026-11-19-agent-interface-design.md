# GelFigure 本地 Agent 接口与配套 Skill：方案草案

日期：2026-11-19。基于当前 v0.6.16 源码检查和合成图最小调用验证。
状态：架构与范围建议；已纳入用户补充的出图前信息核对要求。尚未实施或安装 API、CLI、MCP 和 skill；下文命令、文件名和接口名均为拟定契约。
用户已选择：本地 Agent 优先。用户可以提供作图要求，也可以授权 Agent 从相关实验记录提取信息；必要信息有歧义时，先提问并解决，再正式出图。

## 1. 目标与结论

让用户在自己的 Agent 中提供原始胶图和自然语言要求，由 Agent 调用 GelFigure 完成识别、标注、规范检查、预览及修改，最终取得可用于论文排版的图稿、可继续编辑的项目和处理记录。

可行，且无需重写图像处理与排版。推荐先为现有引擎增加受控的程序接口，以无界面 Chromium 运行；本地 CLI 和 MCP 共用这一接口，skill 指导 Agent 正确使用。网站继续保留当前静态、离线可用的形式。

工具负责可检查的文件、几何和格式规范。实验身份、样本命名、Marker 型号和模糊条带的判断不能仅凭自动出图宣称正确；输出应区分成功、待核对和失败。

## 2. 已有能力与本次验证

已读源码：`js/engine.js`、`js/app.js`、`js/render.js`、`js/export.js`、`js/pptx.js`、`js/ui.js`、项目恢复与测试实现。

- `App.load/readInput`：原始文件加载、自动识别与处理。
- `Engine`：灰度分析、转正、泳道、条带和 Ladder 匹配。
- `App.S`、`App.renderState`、`App.buildFigure`：完整可保存状态与统一出图。
- `App.preflight`：现有分辨率、过曝、削顶、字号、线宽、重叠等检查。
- `Export`：PNG、TIFF、SVG、处理记录；`PPTX.build`：原生可编辑文本和形状。
- `App.projectBlob/openProject`：携带原始图像、校验值与标注的 `.gelfig`，可回到网页继续编辑。

本次在隔离、离线的无界面 Chromium 中，直接调用原有函数加载合成 16-bit TIFF，识别出 11 条泳道和 1 个 Marker，写入名称，生成 PNG/TIFF/SVG/PPTX/项目文件。重新打开项目后泳道、裁切和 Marker 几何一致；未发起外部请求，未出现运行错误。检查同时保留了合成图过曝和标签拥挤提示。

该实验只证明现有调用链可复用；不等于公共接口已完成，也未验证所有真实胶图或所有 Agent 宿主。

## 3. 路线比较

| 路线 | 优点 | 代价与局限 | 建议 |
|---|---|---|---|
| 稳定程序接口 + 本地无界面浏览器 + CLI/MCP | 复用现有识别、字体测量、SVG 和 PPTX，维护一套逻辑 | 首次需 Node 和浏览器运行时；需接口及质量报告适配 | 首选 |
| 纯 Node/Python 重写计算与绘图库 | 后期可更轻量，方便服务部署 | 当前依赖 Canvas、SVG DOM/getBBox、字体布局；容易与网页结果分叉 | 以后有性能或分发证据再做 |
| Agent 模拟鼠标点击网站 | 小型演示容易，立即有可见页面 | DOM/布局变化会失效，状态难复现，批处理和异常处理弱 | 人工回退，非主要接口 |

## 4. 总体结构

自然语言 → Agent + gelfigure skill → CLI 或 MCP → 统一 Job Runner → 浏览器内 GelFigure API → 现有 Engine/Render/Export → 图稿、项目与检查报告。

### 4.1 浏览器内受控 API

增加版本化的 `GelFigureAPI`，封装 load/analyze/apply/render/check/save 等能力。外部不能任意赋值 App.S，也不接受任意 JavaScript/eval。参数先做 JSON Schema 与语义验证，再调用现有应用逻辑。

现有 App.S 是内部实现，包含零基索引、旋转坐标、缓存和兼容字段，不适合作为公共 API 直接暴露。接口应返回稳定的数据对象，并在内部完成转换。

需要抽出或补足的部分：

- 现有 App.load 会捕获错误并 alert，API 模式应返回类型明确的错误；不能以“没有弹窗”判断成功。
- 当前 preflight 多为文字和回调，增加稳定 issue code、数值 evidence 与建议操作；不通过解析中英文文案判断状态。
- 全图总宽的求解目前位于 UI 事件中，应成为可调用操作，区分总图宽和胶图宽。
- 代理模式避免写入普通用户的历史、偏好与 Marker 收藏；不触发赞助、更新、下载弹窗。
- 记录决策来源：user / detector / agent proposal，区分用户预期与图像检测证据。

### 4.2 本地 Job Runner

运行时固定 GelFigure 版本与匹配的 Playwright/Chromium。首版每个任务一个隔离浏览器 context，同一 App 页面不并发处理多张不同胶图；批处理通过任务队列串行，后续再引入独立 worker。

运行前显式确定默认参数、Marker 库、字体及处理配置，避免继承用户浏览器上次操作。结果写入新的任务目录，失败不得留下看似完整的正式交付；用 manifest 标明每个产物是否成功。

图片处理与导出默认断网。CLI 可直接执行；MCP 使用 stdio，无需用户暴露 HTTP 服务、配置账户或提供 API Key。若内部需本机页面服务，只供本任务使用，不提供可任意读取目录的文件服务。

网站仍无运行依赖；Node、Playwright 和 MCP SDK 位于独立的 agent 工具分发包，CLI/MCP 不复制出图算法。

## 5. 先理解、确认信息，再正式出图

用户提供图片，以及以下信息源的任意组合：自然语言要求、相关实验记录、明确授权可检索的实验数据位置。实验记录的访问使用宿主已有的文件/连接器工具，GelFigure 本身不绑定某一家实验记录系统。

### 5.1 分为准备阶段与执行阶段

准备阶段：读取图片与授权记录 → 识别泳道/条带 → 建立事实表与作图方案 → 汇总歧义 → 必要时向用户提问 → 合并回答 → 参数及版式预检查 → ready_to_render。

执行阶段：对已经确定的方案生成最终图稿 → 自动检查产物 → 返回图稿、项目和报告。

准备阶段可进行无损分析、尺寸估算、字体/排版试算和诊断缩略图，以获得提问所需证据；不把未确认的科学标注作为正式图稿交付。后端无需向用户暴露内部试算。这样可以提前发现泳道数与样本数不一致、图像有效分辨率不足、指定字号与总宽冲突等问题。

### 5.2 确认对象是语义信息，不是所有默认参数

按“用户明确提供 / 实验记录明确记载 / 图像检测 / 默认样式 / 尚未解决”记录来源。关键字段包括：

- 图像属于哪次实验、记录是否与该图片对应。
- 胶种、图像方向、从左到右的实际泳道顺序及泳道名称。
- 哪些是 Marker、确切型号或用户提供的条带大小、单位；模型匹配分数不等于已确认货号。
- 要保留的泳道、分组/条件与样本的关系、目标条带标注的含义。
- 必须满足的图宽/格式等输出约束；未指定的字号、边距等使用明确的默认 profile。

用户没有给字号不必单独提问；用户记录没有样本顺序则不能凭条带长相编造。实验记录与当前指令冲突时展示冲突并询问；不能以固定来源优先级静默解决。记录事实保留文件/实验条目/表格行等可追溯引用。

### 5.3 一轮理解后集中提问

Agent 先读完整个相关上下文并进行初步分析，再集中问当前所有影响出图的关键问题，优先提供可选答案和简短推荐；不要发现一个字段就立即打断。回答到达后仅追问仍未解决或新出现的依赖。

示例：图片检测到 9 道，记录仅列出 7 个样本，两个边缘可能是 Marker。Agent 应询问“两侧是否都是 Marker，7 个样本是否按记录顺序从左到右”，而不是先把全部编号改成实验名称再让用户返工。

用户回答“不知道型号”不应陷入重复提问。可询问是否提供条带大小/校准点，或明确选择暂不做分子量标注；把缺失项变成用户接受的省略，而非编造一个型号。

若相关信息已经明确，Agent 给出简短的将采用设置说明即可执行，不增加一律要求用户再点一次确认的流程。用户明确指定的版式选择不因默认 profile 而被替换。

### 5.4 在工具层增加出图前关口

拟增加 `prepare` / `check_plan` 阶段，返回 `awaiting_answers`、`ready_to_render` 或 `failed`。`awaiting_answers` 包含机器可读的 question id、相关字段、冲突证据、选项和影响。

最终 `render` 使用准备结果的 projectRevision、planDigest 与输入校验值，检查：必要字段有合法值或明确的省略策略、泳道引用有效、没有未决的阻塞问题、图像与参数未在确认后发生改变。关键字段或图像变更时回到核对；纯布局调整仍需做版式预检查。

这类关口能拦截漏填、冲突和失效引用，不能从技术上证明模型已经正确理解所有实验语义；因此同时需要 skill 行为测试和事实来源记录。

最终出图仍可能出现解码、内存、字体、编码失败或新的质量问题。能在已确认要求内处理的技术问题自动处理；需要改变科学标注、删除泳道或放宽用户约束时返回待问问题。目标是尽可能把语义确认与可预判的问题前置，不能承诺未出图前已保证任何图像都能“完美”。

## 6. 最小公共工具集

以下名称为建议，CLI 和 MCP 共用输入输出模型。

| 能力 | CLI 示例 | MCP 工具 | 返回 |
|---|---|---|---|
| 环境检查 | `gelfigure doctor` | 首次调用时返回运行时信息 | 引擎/浏览器/字体/读写能力 |
| 查找型号 | `gelfigure ladders --query SM0311` | `gelfigure_list_ladders` | ID、名称、胶种、条带、参考带、来源 |
| 分析胶图 | `gelfigure analyze --input gel.tif --out runs/a1` | `gelfigure_analyze` | 项目、稳定泳道 ID、检测结果、诊断预览与检查 |
| 准备并核对方案 | `gelfigure prepare --analysis runs/a1/analysis.json --spec figure.json` | `gelfigure_prepare` | 就绪状态、问题清单、已解析方案与 revision/digest |
| 应用方案出图 | `gelfigure render --project runs/a1/project.gelfig --spec figure.json --out runs/a2` | `gelfigure_render` | 图稿、项目、manifest、报告 |
| 对话修订 | `gelfigure revise --project runs/a2/project.gelfig --ops changes.json --out runs/a3` | `gelfigure_revise` | 新修订及修改摘要 |
| 规范检查 | `gelfigure validate --project runs/a3/project.gelfig --profile journal-basic` | `gelfigure_validate` | 机器可读的问题与检查覆盖范围 |

Agent 使用 MCP 或 CLI，不重复执行同一任务。准备后的回答可作为更新参数再次调用 prepare；提问由宿主原生提问工具完成，没有专用工具时使用正常对话并等待用户回答，不能以超时视为确认。首版仍需宿主具有本机执行/文件访问能力。

## 7. 参数和状态契约

### 7.1 人类输入与内部坐标分开

公共输入使用清晰的 laneId、1-based 用户泳道号和显式单位，不接受无坐标系的裸 x/y。分析阶段生成稳定 ID；不因改名、隐藏或同一项目修订而改变。重识别导致拓扑改变时返回 ID 对照和失效引用；修订带 expectedRevision，防止把旧指令作用于新泳道。

底层当前使用“旋转后原图像素绝对坐标”，API 内部负责转换。对话里的“1000 bp 附近”与“500 px 高度”应是不同类型的定位条件，并返回最终采用的实际条带位置。没有可靠参照时不能强行给条带标定分子量。

### 7.2 方案示例（拟定）

```json
{
  "schemaVersion": "1",
  "expectedRevision": "revision-returned-by-analyze",
  "gelType": "dna",
  "laneLabels": [
    {"laneId": "lane_01", "text": "M"},
    {"laneId": "lane_02", "text": "WT"},
    {"laneId": "lane_03", "text": "KO"},
    {"laneId": "lane_04", "text": "Rescue"}
  ],
  "markers": [{"laneId": "lane_01", "ladderId": "gr1kb", "unit": "bp"}],
  "layout": {"figureWidthMm": 85, "fontPt": 7},
  "exports": {"dpi": 600, "formats": ["png", "svg", "pptx"]}
}
```

`figureWidthMm` 是包含名称、单位和边距的总图宽。默认参数在 resolved-spec 中补齐，不混同 `gelWidthMm`。示例中的四个 ID 必须来自该输入的分析结果，不能凭位置编造。

### 7.3 状态与结果

- `succeeded`：请求的文件生成成功，所选可执行规范检查通过；不等于实验事实或投稿审查已获确认。
- `needs_review`：已产出草稿/项目，但存在未决的型号、命名、分辨率、过曝或版式问题。报告指明问题、位置、证据和下一步。
- `failed`：参数非法、输入损坏、不支持、运行时缺失、执行失败等，返回错误码与可操作信息。

CLI 约定 0/2/1 分别对应上述状态；MCP 返回相同结构，不把业务待核对状态包装为协议崩溃。若只有部分格式成功，返回每个产物状态，整体不能宣称全部成功。

分析结果包含 detector match score，但它不是经校准的“正确概率”。不要直接设置例如“90% 就可免核对”的门槛；需要使用候选差异、实际匹配条带数、残差、缺失条带和用户提供的型号等证据。

## 8. 配套 Skill

建议发布一个入口 `gelfigure`，普通自动发现可用，CLI 为通用回退，MCP 配置按宿主附带安装说明。SKILL.md 使用可移植的 Markdown，不依赖另一个私人 skill 或固定用户名路径；Codex 的 agents/openai.yaml 为可选元数据，其他宿主需分别验证加载行为。

建议结构：

```text
gelfigure/
  SKILL.md
  agents/openai.yaml
  references/request-schema.md
  references/review-and-repair.md
  references/examples.md
```

skill 的职责：

- 根据胶图整理、泳道标注、Marker 和出图请求触发，不误接普通统计图或 Western blot 工具任务。先理解用户要求和授权实验记录，建立带来源的事实表。
- 把用户语义映射为 JSON：样本名称、胶种、型号、分组/条件、尺寸和格式；明确哪些来自用户、哪些来自自动检测。
- 准备阶段完成图片分析、事实核对、歧义提问和参数预检查，必须达到 ready_to_render 后才交付正式成图。宿主支持图像观察时读取诊断预览；不支持时记录视觉核验未执行，不把这一缺口说成已完成。
- 处理“改第二个名称”“Marker 在右侧”“全图宽 85 mm”等连续对话，不重头识别、丢掉此前手工定位。
- 所有数值、图像处理、导出和校验通过工具完成；skill 不内置第二套绘图脚本。
- 先完成一轮理解，再集中提问；用户/记录已明确的信息不反复询问。缺少关键实验含义不能擅自填默认值；常规样式可采用公开的默认 profile。
- 返回预览、下载文件、可编辑项目和未决问题，不仅回复“已完成”。

## 9. “规范图”的定义

首版提供版本化的通用基础 profile，而非声称符合所有 Nature/Science/Cell 投稿要求。用户可传入具体期刊的宽度、最小字号、输出格式等规则；明确标记自动可检查项、需要视觉检查项和工具无法验证项。

可复用或新增检查：

- 总宽/物理尺寸、导出 DPI、胶图有效 DPI、字体/最小字号、线宽、裁切边界、已覆盖的文字冲突。
- 原图过曝与显示削顶分别报告；输出 600 dpi 不代表原始胶图有效分辨率达到 600 dpi。
- DNA/protein 单位一致、Marker 与样本名数量对应、未匹配条带不得伪装成已识别条带、外推大小保留近似标记。
- 删除泳道/拼接、Gamma 等处理记录与图注说明；默认仅使用已有整体线性调整，不引入局部补带、去条带或生成式修图。
- 用户未要求时不自动删泳道、改变实验名称或编写阳性结论；低信号本身不是需要“修好”的缺陷。
- PPTX、`.gelfig` 用于编辑和复现，可能携带未裁切图像；与最终发表图分别列出。

现有 preflight 的覆盖不完整，API 化时需要补齐结构化编码、实际可见 Marker 判断、自由文本和富文本的最小字号/边界、隐藏裁切对象等，不能仅把旧文案转 JSON 就称为全自动规范校验。

## 10. 输出、复现与本地边界

每次任务输出独立目录：预览 PNG、诊断叠加图、所需图稿、`.gelfig`、resolved-spec.json、quality-report.json、manifest.json 和必要的图注说明。原始文件只读，输出默认不覆盖已有文件。

manifest 记录原图 SHA-256、输入/输出校验值、工具/API/浏览器版本、字体环境、完整解析参数与修订关系。纯时间戳不同不应导致复现测试失败；固定环境下核验像素、几何、标注和参数一致，而非强求含时间戳的 PPTX/gzip 文件逐字节一致。

跨平台字体会改变布局：首版检测并报告字体可用性与替代，锁定运行环境；不未经授权分发 Arial 等字体。若需要跨平台高度一致，可另选有再分发许可的字体并让网页和工具同步支持，作为单独的实现决策。

MCP 文件访问限定本任务输入/输出根目录，处理路径穿越、符号链接越界和输出冲突；工具不接受任意脚本或远端图片 URL。图像尺寸/内存/时间设上限，失败后不无限重试。runtime 用浏览器隔离运行。

GelFigure 执行端默认只在本机处理、无外部请求；用户的 Agent 是否把预览送到云端模型，取决于宿主及模型设置。本地工具不代表整个 Agent 系统必然离线。

## 11. 分阶段交付与验收

### P0：统一接口、CLI 和图稿闭环

抽出 API facade/typed issues，支持原图与项目文件输入、明确的泳道/Marker/常用标注、整体图像调整和受控布局。PNG/SVG/项目/预览/报告为第一条验收路径，TIFF/PPTX 复用现有导出并随首个可用版本验证交付。实现安装诊断、固定版本、隔离设置与任务目录。

验收：不用点击页面就能从 TIFF 出图并打开项目继续编辑；文件损坏和不支持格式可明确失败；修订不丢手动定位；同环境重复任务不受个人偏好干扰。

### P1：MCP 和配套 Skill

MCP 接到同一 runner，提供上述工具。skill 包含输入语义、待核对问题处理、连续修订、质量边界及示例。至少一个支持终端的宿主和一个 MCP 宿主完成端到端验收；不能仅凭 Markdown 相同宣称所有 Agent 即装即用。

验收：用户说一句话可得到图、可编辑项目与报告；继续修改名称/单位/尺寸时复用原项目；信息冲突时只问关键问题，识别失败时保留草稿并解释。

### P2：批处理、模板与分发优化

多个独立胶图按统一样式批量生成、失败可单独重试；同一胶的多曝光沿用已有能力并保留选择依据。补充本地真实回归集与宿主适配，再根据数据考虑常驻进程、缓存、独立桌面打包。

多张不同胶图拼成一个论文多面板图是另一项排版能力：当前多文件能力主要针对同胶多曝光，不能直接声称已有多胶拼版。云端 HTTP API、多用户服务和定量分析不作为首版依赖。

### 质量验收集

- DNA、蛋白、彩色/灰度、16-bit TIFF、双 Marker、弱/无条带、过曝、倾斜/镜像、错误型号和模糊候选。
- 名称数与泳道数不一致、裁切重建、编号、手工校准/隐藏删除、多个 Marker 的作用域、项目复原。
- 请求非法、版本不兼容、失效 revision、缺字体、空间不足、执行中断、并发串扰、输出部分失败和权限越界。
- CLI 与 MCP 同方案结果一致；API 与网页经同一引擎的像素/几何/标注一致；PPTX 结构和必要的原生应用目视验证。
- skill 行为验证：知道何时自动完成、何时返回 needs_review，不编造型号、样本或生物学结论。

## 12. 建议首期决策

采用本地 CLI + stdio MCP + 一个可移植 skill，首版复用固定版本的浏览器引擎，网页和 Agent 共用算法及输出格式；把“生成、检查、核对、修订”作为完整闭环。

此草案供确认开发范围；当前正式发布版和 MIT 许可证不做修改。


## 13. 运行时普适性：没有 Chrome 怎么办

### 13.1 修正一个容易误解的前提

无界面 Chromium 不要求用户预先安装 Google Chrome。Playwright 可以管理与自身版本匹配的 Chromium，也提供独立 headless shell 安装选项。系统 Chrome/Edge 与工具自己的浏览器运行时是两回事。

推荐的首版产品形态是由 GelFigure 安装器管理运行时：

- 常规安装包/引导安装一次性获取匹配的执行环境，后续本地调用无需浏览器界面或浏览器账户。
- 提供对应 Windows/macOS/Linux 和受支持 CPU 架构的预打包版本，尽量把 Node 与匹配的 Chromium 一起管理，避免要求用户手动配置。
- 提供包含运行时的离线包，供下载受限或不允许运行时联网安装的环境使用。
- 已有兼容 Chrome/Edge 可作为显式兼容选项，但不把任意系统版本当默认，以免渲染不可复现。
- Linux 最小系统仍可能缺少系统库，不能承诺一份二进制在任意发行版运行；需列明支持矩阵并用 doctor 检查。

这种方案对用户不要求 Chrome，但执行器内部仍使用浏览器内核，体积较大。安装体验与是否含浏览器内核是两个不同指标。

### 13.2 真正无浏览器：可行，但属于架构改造

抽出环境无关的图像处理与状态内核，并使用共同的布局/场景模型，分别接网页和原生绘图后端。可评估 Skia Canvas 或 resvg 等现成组件；它们是候选，不是已经验证兼容的替代件。

需要处理的实际依赖：

- PNG/JPEG 等目前依赖浏览器 Image/Canvas 解码；TIFF Deflate 与项目压缩也依赖浏览器 Web API，需跨运行时适配。
- 当前字体测量来自 Canvas，PPTX 对象位置从 SVG DOM 的 getBBox 得到，不能只替换一个图片导出函数。
- 无浏览器后端应从共享布局/场景模型直接导出 SVG、栅格图和 PPTX，避免维护两套不同排版。
- 字体、颜色、透明度、富文本、旋转、拼接和图片处理需要与现有网页做实际回归；不能承诺换库后像素完全一致。
- 原生组件也有各系统/CPU 的二进制依赖；“不含浏览器”仍不等于“无需安装任何运行时”。可用各平台自包含程序改善安装体验。

### 13.3 不推荐作为默认的替代

Docker 适合服务器/复现环境，不应让普通科研用户为了出图先安装 Docker。远端 API 可减少本机安装，却涉及图片上传、服务维护与网络依赖，不符合当前本地优先。只支持聊天、无法启动本地工具也无法连 MCP 的宿主不能仅靠 skill 执行处理，需要宿主提供相应能力。

### 13.4 调整后的建议

API、确认协议、skill 与绘图后端解耦。首个可用版本采用用户无须自行安装 Chrome 的受管/预打包运行时；把“无浏览器原生后端”设为独立验证里程碑，而不是首版承诺。若用户明确要求禁止使用任何浏览器内核，则先做原生后端可行性与输出一致性验证，再确定完整开发计划。

用户体验目标：安装一次 GelFigure Agent 工具，Agent 读取图片与记录，必要问题在出图前问清，准备就绪后直接输出全套图稿。


## 14. 运行时资料依据

本次核对的官方/项目文档：

- Playwright 浏览器管理：https://playwright.dev/docs/browsers 。不同 Playwright 版本使用匹配的浏览器二进制；提供 Chromium headless shell 与 `--only-shell` 安装选项，不依赖用户预装 Google Chrome。
- Playwright 作为库：https://playwright.dev/docs/library 。本机程序可启动独立浏览器实例与隔离 context。
- resvg-js：https://github.com/thx/resvg-js 。提供 Node 原生与 WebAssembly SVG 渲染后端、字体和边界能力，可作为无浏览器后端候选；不能直接代替现有所有 Canvas/DOM/PPTX 逻辑。
- @napi-rs/canvas：https://github.com/Brooooooklyn/canvas 。提供 Skia Canvas 与字体测量，存在明确平台/CPU 支持矩阵；需要在 GelFigure 的实际工作流中验证。

这些资料支持技术路线判断；当前只完成既有浏览器引擎的最小调用验证，未实施或验证候选原生/WASM 后端。
